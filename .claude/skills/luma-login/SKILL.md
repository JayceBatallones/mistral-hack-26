# Luma Login via Passkey

Automate the Luma (lu.ma) passkey login flow and land on the authenticated events feed.

> This SKILL.md was generated by video-frame-reader using **parallel subagent analysis** —
> one agent per keyframe, results synthesized into this workflow.

## Prerequisites

- A saved passkey for `luma.com` in the browser's credential manager (Chrome built-in, 1Password, or OS passkey store)
- A Chromium-based browser accessible via the browser-tools skill

## Workflow

### Step 1 — Navigate to lu.ma

```
Navigate to: https://lu.ma
```

**What you see (Frame 1 analysis):**
- Centered auth modal, no redirect to `/login`
- Heading: **"Welcome to Luma"**
- Subtext: "Please sign in or sign up to continue"
- Empty email input field (`type="email"`)
- Three buttons:
  - **"Continue with Email"** (dark/black primary button)
  - **"Sign in with Google"** (with Google icon)
  - **"Sign in with Passkey"** (with passkey icon)

**Automation selectors:**
```
button[text="Continue with Email"]
button[text="Sign in with Google"]
button[text="Sign in with Passkey"]
input[type="email"]
```

---

### Step 2 — Click "Sign in with Passkey"

Click the **"Sign in with Passkey"** button.

> Alternative: Clicking/focusing the email input field may also auto-trigger the browser's saved passkey credential picker.

---

### Step 3 — Handle Browser Credential Manager Dialog (Dialog 1)

**What you see (Frame 2 analysis):**
- Browser-native dropdown/dialog overlaid on the Luma modal (outside page DOM)
- Title: **"Use a saved passkey for luma.com"**
- A saved account entry visible (email address + "Passkey" label)
- Button: **"Continue"**

**Action:** Click **"Continue"** or press `Enter`.

> This dialog is NOT in the page DOM — use keyboard navigation (`Tab` to focus, `Enter` to confirm) or browser-tools native dialog handling.

---

### Step 4 — Handle Platform Authenticator Dialog (Dialog 2)

**What you see (Frame 3 analysis):**
- A second system-level dialog (OS or browser built-in passkey authenticator)
- Distinct from Dialog 1 — different dialog chrome/styling
- Shows the same saved account entry
- Secondary option: "Add a different account" or similar

**Action:** Confirm authentication (biometric, PIN, or auto-resolves on configured devices).

> On automated systems this may resolve automatically. If it hangs, wait for user confirmation before proceeding.

---

### Step 5 — Verify Authenticated State

**What you see (Frame 4 analysis):**
- URL navigates away from the login modal (to `lu.ma/home` or similar)
- Full Luma events dashboard loads
- Page heading: **"Events"**
- Left sidebar with date filter: **"Today"**
- Event cards with:
  - Event title, thumbnail, status badges (**"LIVE"**, date badges)
  - Date group headers (Today, Tomorrow, upcoming dates)
- No login modal visible

**Automation assertions:**
```
✓ URL does not contain a login modal state
✓ Page heading contains "Events"
✓ Event cards present (at least 1)
✓ No auth modal visible in DOM
```

## Parallel Execution Pattern

When this skill is invoked as part of a larger workflow, the verification step (Step 5) can be parallelized with post-login data fetching:

```
[Step 5a] Assert authenticated state (Events heading visible)
[Step 5b] Scrape upcoming events list               ← parallel
[Step 5c] Check for any notification badges         ← parallel
```

Use Task tool with `run_in_background: true` for 5b and 5c while 5a resolves.

---

## Failure States & Recovery

| Symptom | Likely Cause | Recovery |
|---------|-------------|----------|
| Modal still visible after passkey flow | Platform authenticator timed out | Re-click "Sign in with Passkey" |
| Dialog 1 does not appear | No saved passkey in browser | Fall back to "Continue with Email" |
| Dialog 2 hangs indefinitely | Biometric/PIN required from user | Wait, then continue |
| Events page shows 0 cards | Account has no events (still authenticated) | Assert heading "Events" is sufficient |
| Redirected to error page | Passkey credential expired | Re-register via "Continue with Email" |

## Notes

- The login modal is **inline on the homepage** — no separate `/login` URL
- Both dialogs are **outside the page DOM** — handle via keyboard or browser-tools native dialog API
- No password is typed at any point in this flow
- The authenticated events feed groups events by: **Today**, **Tomorrow**, upcoming dates
